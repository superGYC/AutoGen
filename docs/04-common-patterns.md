# 04 — 多智能体常见设计模式

> 无论你选哪个框架，这些模式是通用的。

---

## 模式 1：分层架构（Hierarchical）

```
         ┌─────────────┐
         │   Manager   │ ← 经理 Agent：分配任务、协调、决策
         └──────┬──────┘
                │
    ┌───────────┼───────────┐
    ▼           ▼           ▼
┌───────┐   ┌───────┐   ┌───────┐
│Agent A│   │Agent B│   │Agent C│ ← 执行 Agent
└───────┘   └───────┘   └───────┘
```

**适用**：CrewAI（原生支持）、LangGraph（可构建）

**场景**：
- 内容团队（主编 → 记者/摄影师/编辑）
- 软件开发（架构师 → 前端/后端/测试）
- 客服中心（主管 → 一线客服/技术支持）

**关键点**：
- 经理 Agent 的能力决定整个系统的上限
- 经理不能成为瓶颈：如果它挂了，全队停摆
- 可以给经理加 "planning" 工具，让它先做任务拆分

## 模式 2：路由/网关（Router / Gateway）

```
            ┌─────────────┐
            │   Router    │ ← 意图识别 + 分发
            └──────┬──────┘
                   │
      ┌────────────┼────────────┐
      ▼            ▼            ▼
  ┌───────┐   ┌───────┐   ┌───────┐
  │ 客服   │   │ 销售   │   │ 技术   │
  └───────┘   └───────┘   └───────┘
```

**适用**：LangGraph（最佳）、CrewAI（Flows）、AutoGen（可模拟）

**场景**：
- 智能客服入口："我要退款" → 售后 Agent，"怎么升级" → 技术支持 Agent
- API Gateway：根据请求类型路由到不同处理 Agent

**关键点**：
- Router 本身可以很简单（一个 LLM 判断意图）
- 也可以很复杂（基于向量检索 + 规则引擎）
- 常见陷阱：Router 误判导致用户被转来转去

---

## 模式 3：反射/自我修正（Reflection）

```
┌─────────┐    ┌─────────┐    ┌─────────┐
│ Generate│───▶│ Reflect │───▶│ Revise  │
│  生成   │    │  反思   │    │  修正   │
└─────────┘    └────┬────┘    └────┬────┘
                    │ OK?            │
                    └──── no ────────┘
                         yes
                          ▼
                    ┌─────────┐
                    │  Output │
                    └─────────┘
```

**适用**：LangGraph（原生循环支持最佳）、AutoGen（对话循环）

**场景**：
- 代码生成：写代码 → 检查 bug → 修复 → 再检查
- 写作：起草 → 自我批评 → 改写 → 再评估
- 翻译：初译 → 审校 → 润色

**关键点**：
- 设最大迭代次数，防止无限循环
- "反思 Agent" 要和 "生成 Agent" 用不同的 prompt，甚至不同的模型
- LangGraph 的 `add_conditional_edge` 天然适合这个模式

## 模式 4：并行执行 + 汇总（Map-Reduce）

```
         ┌─────────────┐
         │   Splitter  │ ← 把任务拆成 N 个子任务
         └──────┬──────┘
                │
    ┌───────────┼───────────┐
    ▼           ▼           ▼
┌───────┐   ┌───────┐   ┌───────┐
│Agent 1│   │Agent 2│   │Agent 3│ ← 并行执行
└───┬───┘   └───┬───┘   └───┬───┘
    │           │           │
    └───────────┴───────────┘
                ▼
         ┌─────────────┐
         │   Reducer   │ ← 汇总结果
         └─────────────┘
```

**适用**：LangGraph（`Send` API 支持并行）、CrewAI（有限并行）

**场景**：
- 批量数据处理：100 份简历 → 10 个 Agent 并行筛选 → 汇总 top 10
- 多源信息汇总：5 个搜索 Agent 各查一个数据源 → 综合报告
- 代码审查：多个 reviewer 并行检查不同维度 → 汇总问题列表

**关键点**：
- 注意并发控制，别打爆 API rate limit
- Reducer 的 prompt 要明确要求 "整合而非罗列"

## 模式 5：人机协作（Human-in-the-Loop）

```
┌─────────┐     ┌─────────┐     ┌─────────┐
│  Agent  │───▶│ Human   │───▶│  Agent  │
│ 执行    │     │ 审批    │     │ 继续    │
└─────────┘     └─────────┘     └─────────┘
     ↑                              │
     └────────── 反馈修改 ──────────┘
```

**适用**：LangGraph（`interrupt` 原生支持最佳）、AutoGen（`user_proxy`）

**场景**：
- 医疗诊断：Agent 分析 → 医生确认 → 开处方
- 金融审批：Agent 初评 → 风控人工复核 → 放款
- 内容发布：AI 写稿 → 编辑审核 → 发布/打回

**关键点**：
- 明确哪些节点必须人工介入（不能全交给 LLM 判断）
- 给人类足够上下文，别只丢一句 "请审批"
- 超时机制：人类 24 小时不响应怎么办？

## 模式 6：记忆共享（Shared Memory）

```
    ┌─────────────────────────────┐
    │       Shared State          │
    │  {facts, entities, plan}    │
    └────────────┬────────────────┘
                 │
    ┌────────────┼────────────┐
    ▼            ▼            ▼
┌───────┐   ┌───────┐   ┌───────┐
│Agent A│   │Agent B│   │Agent C│
└───────┘   └───────┘   └───────┘
```

**适用**：LangGraph（`State` 天然共享）、CrewAI（Context 传递）、AutoGen（群聊历史）

**场景**：
- 长期对话：客服 Agent 知道用户之前问过什么
- 多轮研究：研究员 Agent 今天搜的，写手明天还能引用
- 团队知识库：所有 Agent 共享一个企业知识图谱

**关键点**：
- 区分 "短期记忆"（当前 session）和 "长期记忆"（持久化数据库）
- 注意状态同步的竞态条件
- LangGraph 的 `checkpointer` 是行业标准实现

## 模式 7：工具共享市场（Tool Marketplace）

```
┌─────────────────────────────────────┐
│          Tool Registry              │
│  [搜索] [浏览器] [代码执行] [SQL]    │
│  [邮件] [日历] [CRM] [Slack]         │
└────────────┬────────────────────────┘
             │
    ┌────────┴────────┐
    ▼                 ▼
┌───────┐         ┌───────┐
│Agent A│         │Agent B│
└───────┘         └───────┘
```

**适用**：所有框架（LangChain Tools、AutoGen Tools、CrewAI Tools）

**场景**：
- 企业级 Agent 平台：每个 Agent 按需调用共享工具
- 安全管控：谁有权调用 "转账" 工具？需要审批吗？

**关键点**：
- 工具描述（description）的质量直接决定 Agent 调用准确率
- 给工具加权限控制，不是所有 Agent 都能删数据库

## 🧠 模式组合实战

### 完整案例：企业智能助手

```
用户输入："帮我安排下周去深圳的客户拜访"

[Router] 识别意图："日程安排 + 差旅"
    │
    ├──▶ [Research Agent] 查深圳天气、客户地址
    │       │
    │       ▼
    ├──▶ [Calendar Agent] 查空闲时间（并行）
    │       │
    │       ▼
    ├──▶ [Travel Agent] 查机票/酒店（并行）
    │       │
    │       ▼
    [Reducer] 汇总所有信息
        │
        ▼
    [Human-in-the-loop] "我帮你安排了这些选项，请确认"
        │
        ▼
    [Action Agent] 确认后：订机票 + 订酒店 + 写日程
```

这个流程里用到了：**路由 + 并行 + 汇总 + 人机协作**

## 📖 总结：模式速查表

| 模式 | 核心问题 | 首选框架 |
|------|---------|---------|
| 分层 | 谁管谁？ | CrewAI |
| 路由 | 分给谁？ | LangGraph |
| 反射 | 错了怎么办？ | LangGraph / AutoGen |
| Map-Reduce | 怎么并行？ | LangGraph |
| 人机协作 | 人在哪介入？ | LangGraph |
| 记忆共享 | 怎么记住？ | LangGraph |
| 工具市场 | 用什么能力？ | 全部 |

---

*设计模式是骨架，具体实现可以跨框架迁移。理解模式比死记 API 更重要。*
